# 配布通知の書式

**なぜこのファイルが在るか。** 2026-09-01、v1.7.52 の告知で 2 件の誤りを 7 面へ
配った。うち 1 件（`validate` の呼び方）は、**v1.7.50 の報告書で私自身が 3 段に
整理した内容**を使わなかったもの。⇒ **報告書に書いた整理が、次の告知に反映される
経路が無かった。** このファイルがその経路。**告知を書く前に必ず読む。**

---

## 1. 行ごとに出所を書く

```
[撃った] その場でコマンドを実行して得た値
[読んだ] 実装を読んで得た値（行番号を添える）
[導いた] 上の 2 つから推論した値   ← ⚠️ 最も誤りやすい
```

⚠️ **v1.7.52 の 2 件はどちらも [導いた] を [読んだ] のように書いた。**

- 「`headers` を書くと error」← 語彙からの削除**意図**から導いた。実際は
  warning / exit 0。**同じ diff に `errors.append` の実例が 3 つ、
  `result.errors == []` を固定したテストまで在った**
- 「`validate` 引数なしで全件」← 全件を撃つ**意図**から導いた。実際は exit 2。
  **`--help` を 1 行読めば分かった**

⇒ **[導いた] と書けない行は、書く前に撃つか読む。**

**もう 1 本、受け手側の軸がある: その行は誰が再検証できるか。**
[撃った/読んだ/導いた] は書き手の分類で、受け手が要るのは
**「自分の面で撃てるか」**。⚠️ 値は受け手ごとに変わるので、
**「撃てない」ではなく「どの面なら撃てるか」を書く** ——
そして**送り手のその見立ては保守的に外れる**。生成器の挙動は「生成する面」で
なくても撃てる（要るのはプロジェクトではなく fixture）。本当に面が要るのは
**ランタイム挙動**（iPad の size class の類）だけ。ある面は「撃てない」と
書かれた生成器の主張を fixture で 2 版比較し、引用ではなく実測で掲載した —
受け手が「撃てない」を確かめずに引用へ倒すと、撃てたはずの主張が
引用のまま残る。⇒ 書くのは「どの面なら」に加えて**「何が要るか」**
（fixture で足りる / ランタイムが要る）。 ある面はこれで
「実測として書かず、宣言の言葉として引用する」という掲載判断ができた。
「撃てない」とだけ書かれていたら、引用すべきか落とすべきか決められなかった、
という報告つき。

**新属性の告知にはもう 1 行**: 「受け手側に属性名 → 出力先の**手書き対応表**が
無いか」。ある面では手書きの category map に無い属性が**どのカテゴリにも一致せず
緑のまま publish されない**形で、SSoT が宣言した属性が 21 日間どこにも
掲載されなかった（兄弟属性が在ったから不在が読めただけで、単独なら
気づく手段が無かった、と当人の実測）。

⚠️ **出所の明記は「借りる量を減らす」だけで、借りる構造は消えない**（lib レーン）。
clone を持たない純粋な消費機は結論を借りるしかない。⇒ **各行を、その面で
版をまたがず検算できる性質として書く**のが上位の形。

## 2. 結論ではなく性質を配る。ただし判定が閉じるかを見る

```
✗ 結論   「警告 1 行を見落とせば気づかないまま書き続けられます」  ← 借りるしかない
△ 性質①  「気づけるかは Warnings: の基準値が 0 かで決まる」        ← 閉じていない
✓ 性質①∧② 「気づけるのは、基準値を次回と突き合わせる装置がある面だけ。
            基準値が 0 か非 0 かは、装置が在る面での感度の話」
```

⚠️ **配る性質が、それだけで判定を閉じるかを見る。** 閉じない性質は
**「確かめた気になる性質」**になり、②を欠く面が「自分は①だから安全」と読む。
**判定を分けているのは②（装置の有無）だけ。**

## 3. 段を配るときは、軸を名乗る

⚠️ **v1.7.52 で 2 つの軸を 1 本の梯子に混ぜた。** 混ぜると、
**手順を変えた瞬間に段が変わる面**（＝ほとんどの面）が固定属性として引用される。

**軸 A — 面が構造的に該当しうるか**（v1.7.50 台帳の軸）

| 段 | 成立させるもの | 忘れたら |
|---|---|---|
| 強（構造） | config が `test.install` を宣言していない ⇒ `resolve_targets` が空 | **打ち忘れが存在しない** |
| 中（手順） | `test.install.src` ちょうどを渡す | 黙って危険側へ落ちる |
| 弱 | ディレクトリを渡している | **理由にならない**（部分ディレクトリも同じ形で壊れる） |

**軸 B — 呼び方の安全度**

| | |
|---|---|
| `--no-install` | ⚠️ **手順**。毎回打つ必要があり、忘れれば静かに危険側へ戻る |
| 引数を部分集合に絞る | 軸 A が「強」でなければ危険 |

🚨 **軸 B は「安全度の順」であって「置換可能な選択肢」ではない。**

`--no-install` は `Validate only; skip flatten-install even if test.install is
configured`（`--help`）。⇒ **install を必要とする面にとっては別の操作。**
平坦化された `.test.json` を読む UI テストを持つ面が `--no-install` に寄せると、
**テストが 0 件になるのではなく、前回の内容で緑になる。**

⇒ **軸 B を告知に載せるなら「`--no-install` へ降りると install が止まる」を必ず併記する。**

⚠️ **この規則は、このファイルの初版が配られた当日に、ある面が撃って見つけた。**
初版は 3 段を「安全度の梯子」として並べており、**梯子は上に登れることを含意する。**
含意まで書かないと、規則そのものが誤指示になる。

📌 **同じ効果を出す 2 つを並べたら、忘れたときに何が起きるかで分ける。**
`--no-install` と「config に宣言が無い」はどちらも `resolve_targets` を空にするが、
**前者は覚えている必要があり、後者はリポジトリの状態**。

⚠️ **段は面の属性ではなく、面と時点の関数。** 聞くなら
**「あなたはどの段ですか」ではなく「今どれが成立していますか」。**
前者だと受け手が固定属性として答える。

## 4. 露出列には分母と対照を書く

```
scenarios を持つファイル : 886
シナリオ                 : 3861
対照 'status' が在る     : 3861   ← 網が生きていることの対照
対照 'body' が在る       : 3828
'headers' が在る         : 0
```

⚠️ **対照は測定と違う道具で撃つ。** 同じ walker を通すと欠陥を共有する
（`grep` の shim が `.gitignore` を honour して 78% を不可視にしたとき、
対照も同じフィルタを通って一致して見えた）。

⚠️ **走査根を書く。** v1.7.52 で commit 本文の `1189 files` と面の分母 `886` が
食い違って見えた。実際は `886 + 302(ツール側 fixture) + 1 = 1189` で
1 も違わず閉じていた。**食い違いではなく、根が違うだけだった。**

## 5. 範囲の起点を書く

```
✗ 「SHA 945d4fd0…」だけ        → 受け手が tip を撃って「主張と違う」と読む
✓ 「範囲: v1.7.51..v1.7.52（起点タグ → タグ、6 commits）」

⚠️ **SHA はコミット SHA（`^{commit}` 解決済み）と明記する。** 注釈付きタグでは
`git rev-parse vX.Y.Z` がタグオブジェクトを返し、受け手が SOURCE_SHA と
突き合わせると**正しい版で偽の不一致**が出る（2 レーンが同日に踏んだ）。
```

タグ先の commit 単体は 1 ファイル 12 行、範囲は 15 ファイル。**別物。**

⚠️ **タグは CI 緑を実測した commit に打つ — 「release: x.y.z」commit と一致するとは
限らない。** release commit で CI が赤になれば後続 fix にタグが載る（v1.7.52 / v1.7.53）。
一致している版（v1.7.54 / v1.8.0）は結果であって規則ではない。受け手が「タグが
release commit の後ろにある = 動かされた」と読む前に、タグ先の `VERSION` と報告書の
SHA を見る（backend レーンが 4 版まとめ検証で問うた）。

## 5.5 変更は**絶対座標**で書く。差分で書くと、受け手が居ない版を仮定する

⚠️ **告知の宛先は版を持っている。そして送り手はその版を知らない**（面は自分で pin する）。
⇒ **差分で書くと、受け手は「自分に当たるか」を判定するために、送り手が仮定した起点に
自分が居ることを確かめねばならない。その材料は告知の中に無い。**

**実例（2026-09-04、列車の誤り #63）**: ios driver の stderr 変更を **「1.9.8 → 1.9.9 の差分」**として告知した。
受け手の面は **1.9.6** に居り、その面が文字列一致で見ていた文
`scrolled both ways and it is still off the viewport` は **1.9.4〜1.9.7 に実在して 1.9.8 で削除**されていた。
⇒ **告知が名指した区間の外に、その面の実害があった。** 面の集計は 4 パターン中 2 つが
同時に 0 になるところで、**「起きなかった」と読める形**だった。

```
✗ 差分で書く
   「1.9.8 → 1.9.9 で末尾が `that viewport` → `that visible part` に変わりました」
   受け手が 1.9.6 なら、この 2 版のどちらにも自分は居ない

✓ 絶対座標で書く（版ごとの実物を並べる）
   1.9.4 – 1.9.7  "... scrolled both ways and it is still off the viewport"
   1.9.8          その文を削除、"still not hittable" に統合
   1.9.9 – 現行   "... visible part of it <rect> ...; hit point inside|OUTSIDE that visible part"
```

**送り手側の自己検査**（受け手レーンの定式、そのまま採用）:
> **受け手が版 X に居るとき、この告知のどの行を読めばよいかを、2 つ以上の X について
> 自分で答えられるか。** 答えられなければ、まだ絶対座標になっていない。

**表の作り方**（文字列がどのタグ区間に在ったかを撃つ）:
```bash
# ⚠️ 件数ではなく**行を出す**。理由は下
for t in $(git tag --list | sort -V); do
  echo "--- $t"
  git grep -n "<文字列>" "$t" -- Sources/ 2>/dev/null
done
```
⚠️ **件数だけ数えると、コメントと出力を区別できない。** この recipe を書いた直後に
自分で踏んだ: `still off the viewport` を数えると **1.9.8 = 0 / 1.9.9 = 0 / 1.9.11 = 1** と出て、
**その文が復活したように読める**。実体は **1.9.11 の doc comment がその文を引用している**だけで、
出力には無い（引用したのは、まさにこの事例を説明するため）。
⇒ **行を見れば `///` で始まっているのが分かる。件数では分からない。**
[[feedback_one_hit_is_more_dangerous_than_zero]] の形そのもの。

## 5.6 bootstrap が**複数版を飛び越す**なら、載る版を名指す

⚠️ 予告と受け手の実行の間に版が進む。**2026-09-04、2 レーンが独立に踏んだ** ——
告知は 1.8.21 のものだったが、両レーンが撃った時点のディスクは **1.8.23** だった。
どちらも**自分の span を取り直して**検算したので実害は出ていないが、
**予告の span をそのまま検算に使う受け手は、間に挟まった版を見ないまま
「刻印のみ」を確認したことになる。**

⇒ 告知に**この配布後に `~/.jsonui-cli/VERSION` が何になるか**を書く。
受け手は自分の出発点とのズレをその場で見つけられる。

## 5.7 「この配布で **sync が触る面**」を書く。ただし**面の側で測る**

受け手が自分の tree の差分と突き合わせられる形にする。⚠️ **その内訳は
リポジトリ側の diff からではなく、面が実際に vendor している物から作る。**

**実例（列車の誤り #66）**: 「版スタンプ 5 ファイル（sjui / kjui / rjui / test_tools / document_tools）」
と書いたが、**面は 3 または 1** だった —— **test_tools と document_tools はどの面にも
vendor されていない**（bootstrap 経由）。5 は `git diff --stat -- <tool subtrees>` の値、
すなわち**リポジトリ側の数**。⚠️ **同じ報告書の数時間前の節に「面は test_tools を
vendor していない（実測 0 コピー）」と自分で書いてあった。**

```bash
# 面ごとの実測（リポジトリ側の diff ではなく）
for t in sjui_tools kjui_tools rjui_tools test_tools document_tools; do
  find <face> -maxdepth 3 -type d -name "$t" -not -path "*/node_modules/*"
done
```

⚠️ **併せて「変わらないはずのもの」を書く。** 受け手が `jui build` の diff 0 を
**予測の的中**として読めるようになる —— 何も知らずに 0 を見れば「今回は何も無かった」で
終わる（受け手レーンの定式）。**自分が測った範囲と測っていない範囲も名乗る**:
「ソースを読んだだけで、そちらの面に対しては測っていない」と書くと、
**受け手が自分を唯一の反証手段だと理解して撃つ。**

## 6. 配布時刻を書く — `date -u` の出力をそのまま貼る

⚠️ **手で書き直さない。** v1.7.53 で JST の数字に Z を貼って配った（実測 10:12Z を
「19:12Z」と表記）。時刻を残す運用は受け手の照合に使われるので、**単位が偽なら
値が正しくても台無しになる。** 受け手側の言い方では「検査の件数は単位と分母を
名乗る」の単位側の違反。

⚠️ **計器の部分出力も合成を誘発する。** v2.24.0 で watcher に `date -u '+%H:%M:%S'`
（時刻のみ）を印字させ、通知作成時に **UTC の時刻へ JST の日付**を貼った
（「19:12Z」は時刻の単位が偽、今回は日付の出所が偽 — 同じ欠陥クラスの別の綴り。
受け手レーンの照合が検出）。**watcher・ポーリングスクリプトにも `date -u` をフル出力で
印字させ、通知はその行を貼るだけにする。** 欠けた部分を後から手で補うくらいなら、
計器を直してから撃ち直す。

2 件は同じ癖の別の綴り: **2 つの時計の読みを 1 つの文字列に組み立てている**
（JST の数字 + Z / UTC の時刻 + JST の日付）。組み立てる限り、正しい半分が
誤った半分をもっともらしく見せるので、受け手は照合する動機を持たない。
閉じ方は逐語貼り付けのみ — **組み立てた時刻はどれほど自然に見えても出さない。**

⚠️ **時刻を照合する側も、読んだフィールドを名乗る。** commit 日時（`%ci`）と
タグ日時は別のフィールドで両方真になり得る — 食い違いは「相手の誤記」と
「こちらの欄違い」の**両方が予測する**ので、どちらを読んだか言わない照合は
所見にならない（受け手レーンの near-miss 開示より）。

**配布は自動、受入は手動。** ⇒ `bootstrap` と `jui sync_tool` は、
**他レーンが実験を回している最中に計器を差し替える。**
v1.7.52 で、ある面の E2E 実験の腕をまたいで `jsonui-test` が入れ替わり、
**2×2 の 1 ラン分が無効になった**（本人申告: 確認要請が無ければ
腕 D の 3/24 を CPU 60 倍の効果として報告していた）。

⇒ **通知に配布時刻を書く。** 受け手が自分の計測の時刻と突き合わせられるように。

## 7. 観察を書くなら、それを撃つコマンドを添える

⚠️ **繋げた部分が「指示の形」か「観察の形」かで、検算される確率が違う。**
指示は撃たれるので同日に検算される。**観察は撃つ動機が無いので、
誤っていても台帳に載ったまま残る。**

⇒ **撃てない観察は書かない。書くなら撃つ手順を添える。**

🚨 **添えるのは「測った部分を再現するコマンド」ではなく「繋げた部分を反証しに行く
コマンド」。** 前者は必ず成功するので、**添えるとかえって信頼を上げる。**

実例（ある面の自己申告）。観察「複製が古い ⇒ エディタ緑 → validate 赤が作れる」に:

```
✗ cat .mock.schema.json | grep headers   → 観察が偽でも「複製は古い」が返る。
                                            繋げた部分は検算されないまま通る
✓ jsonui-test validate <targets>         → PASSED が返り、繋げた部分が偽だと分かる
                                            （実際 warning / exit 0 だった）
```

⇒ **添えるコマンドが「その観察が偽だったら別の答えを返す」形になっているかを見る。**

## 7.5 「無かった」と「見ていない」を書き分ける

⚠️ **通知の欠落は、受け手からは「変更が無かったこと」と区別できない。**（消費側レーンの
定式、2026-09-03）。⇒ ある面について何も書かなければ、受け手は「そこは動かなかった」と
読む。実際には**測っていない**だけかもしれない。

```
✗ （何も書かない）                 → 受け手は「動かなかった」と読む
✗ 「当方の把握では 0 件」          → 把握は測定ではない。何を見たか言っていない
✓ 「help が動いた葉: 0 件（58 葉を比較）」      ← 測った
✓ 「help の変化は測っていない」                 ← 測っていないと言った
```

実例: `jui build --lint-strings` は不変条件 #4（localize ゲート）をビルドに載せる唯一の
フラグだが、それを足した列車の通知に**葉の粒度の記載が無く**、ドキュメント側は未掲載の
まま 4 か月生き延びた。当時その運用が無かったのが理由だが、**受け手にはその区別が付かない**。

⇒ **変更駆動の運用（受け手が「動いた面」を読んで追随する）を敷いた以上、動かなかったことも
測って書く**。書けないなら「測っていない」と書く。**沈黙は第三の値であって、0 ではない。**

## 7.6 緊急通知は「撃つな」で書く。「版を戻せ」は実行できない

⚠️ **`~/.jsonui-cli` はマシン共有で、配布は上書き。** 消費側に**版を選ぶ手段は無い** ——
ある面が戻せば他の全レーンに効く。⇒ **「1.8.5 のままで作業してください」は、受け手が
実行できない指示**（受け手はそれを試み、共有資源なので動かせないと知る）。

```
✗ 「1.8.5 に留まってください」        → 実行不能。しかも実行しようとすると他面を壊す
✓ 「`jui build` を撃たないでください」 → 受け手が単独で実行できる
✓ 「壊れているのは `jui build` だけ。`verify` / `validate` は無事」  ← 残る道を名指し
```

⇒ **緊急通知の単位はコマンドであって版ではない。** 版で条件を出すと、受け手は版を
動かそうとする。あわせて**戻し方があるなら明示する**（無いなら「無い」と書く —— ある面が
「戻し方が無いなら無いと書いてほしい」と要請した）。

⚠️ **壊れたコマンドが残す痕跡も書く。** 1.8.6 の crash は正規化の**手前**で落ちるので、
`Layouts/Resources/colors.json` が SSoT のフラット形のまま配られ、**モード構造が剥がれた
「別の正しい形に見えるファイル」**が残った。⇒ `git status` の行数でも目視でも異常に
見えない。**「中途半端なツリーが残る」だけでは受け手は探せない。何がどう変わるかを書く。**

## 5.9 **「挙動変更なし」は差分の主張。区間を書かないと嘘になる**

**1 度目は「区間の外に害が在った」、2 度目は「区間の外に変更が在った」。**
**同じ穴の 2 つの向き。**

### 5.10 追補: 判別子は「新しい内容が在る」しか言わない（1.8.35、admin backend）
`grep -c '<この版で足した文字列>'` が 0 → 1 は**配布物に新しい内容が在る**ことを版番号と独立に示す（刻印だけ進んで中身が来ていない形を弁別する）。
だが**古い内容が無い**ことは示さない。追補が純増の版では同じことだが、**置換や削除の版では別の述語**（消えた文字列が 0 件、`ls-files` の 1 → 0 など）を添える。

対で持つなら消失側が外れても出現側が立つ。多語フレーズの `grep -c` は折り返しで動く — 短い、説明文に含まれない語を選ぶ。
**判別子は説明文に現れない句を選ぶ**（1.8.37、受け手の web 面）: 良いコメントを書く版ほど、判別子が**説明**に当たる（1.8.36 は説明文に残った語句、

受け手は `-c` / `-cE` / `-cF` の 3 通りで撃って、どれが立ったかを報告する（BRE の `|` は literal、ERE では選択 — 同じ文字列で値が変わる）。
送り手は **literal の判別子には `grep -cF` を明示**して 1 通りに定める（受け手の backend 面: `|` を含む判別子はシェルと grep の方言で数が割れる。
ベースラインと本測定を同じ読み方で撃たないと、方言差を版の差と誤読する）。

### 5.13 追補 3: **bytecode も挙動ではない**（1.8.36、受け手の backend 面の実測）
「実行行 0」の版（コメントと docstring のみ）に、受け手の**全 code object の co_code ハッシュ**が DIFFERS を返した。正体は Python 3.13+ の
`__firstlineno__`: class の code object は自分の開始行を持つので、**上流の docstring が 1 行増えるだけで下流のクラス本体の bytecode が動く**
（最小 probe: docstring に 1 行足すと `class C` の co_code が変わる）。決着は diff を読むこと（hunk は 1 つ、全行 docstring 内）。
⇒ バイト比較（関数ハッシュ・bytecode）は **同一なら強い / 相違は何も言わない** の非対称な証拠。相違が出たら必ず diff に降りる。
トークン比較（COMMENT と文頭 STRING を落として比べる）は行番号に依存しないので「コードを含むか」にはそちらが向く（同版、別の backend 面）。
⚠️ **ただし Python にしか当たらない**（`tokenize` は Python 専用）。「コメントのみ」の申告を独立に検算できるのは**その言語のトークナイザを持つ面だけ**で、
Ruby / Swift / Kotlin の受け手が行ベースの grep で代用すると、上の偽陽性をそのまま踏む。⇒ 送り手は言語ごとに「何で検算できるか」を添える
（Ruby: `ruby -c` は構文だけ、`Ripper.lex` でトークン / Kotlin・Swift: コンパイル結果の byte 比較は行番号を含み得る）。

### 5.13 追補 2: **mtime は「変わった」ではない。ハッシュ単独も足りない**

**① 🚨 受け手が `shared/` の検算に mtime を使うと、必ず「動いた」に見える**（実測・受け手）:
```
~/.jsonui-cli/shared/core/parent_spec_rules.py  mtime 13:17:51
~/.jsonui-cli/VERSION                            mtime 13:17:51   ← 同時刻
⇒ bootstrap は全ファイルを書き直すので、**動いていないファイルも VERSION と同じ mtime**
中身で判定: git diff --stat v1.8.30..v1.8.31 -- shared → 差分なし
対照:       同じ範囲の document_tools              → 6 files / +226 −11
```
⇒ **告知に「`shared/` が動いたか」を書くときは、`git diff --stat <range> -- shared` の結果を
そのまま載せる**（0 files なら `0 files` と）。**タグを引けない面は mtime しか持たない。**

**② 関数本体のハッシュは、単独では挙動不変を意味しない**（受け手の限界申告・採用）:
```
必要なのは 2 つでひと組:
  (1) 関数本体のハッシュ一致
  (2) **その関数が呼ぶ先の到達可能性**（呼び先が動けば byte 一致でも挙動は変わる）
⇒ 実例では (2) を `grep 'spec_doc|shared_core' check/ → 0 hits` + 現物のファイル一覧が担った
```
⚠️ **行範囲の切り出しにも前提**: `sed` は関数の終端を知らない ⇒
**関数が伸縮する版では偽の不一致も偽の一致も作れる。**
**終端の決め方（次の `^def ` まで、等）を書式に含める。**
⚠️ **そして clone のタグを読んでいる** ⇒ **配布物を見ていない。**
受け手にとって強いのは `~/.jsonui-cli` 側の現物で撃つ形。

**③ 「読んでいる」の弱い版と強い版**（docsite レーンの整理・採用）:
```
弱い  横断的: 行ごとに値が違う ⇒ **定数ではない**ことだけ示す（デコイで除外も確認）
強い  変異的: **1 本だけ入力を変える** ⇒ その行だけ変わる
      ⇒ **そのファイルを実際に読み直している（古い値を持っていない）**まで示す
```
⇒ 台帳には**「片方ずつ」ではなく「弱い方と強い方」**として置く。

**④ 生成器が動いた版では、該当条件の外も測る**（受け手の一般形・採用）:
> **告知の該当条件は「その修正が狙った形」を切る。動いたファイルが生成器そのものなら、
> 条件の外にある生成物も測る。**
実例: `subSpecs` 0 で該当条件は外れるが、**動いたのは HTML/MD ジェネレータ本体**
⇒ 追跡している 60 ページを再生成 → 42 ファイル差分、**時刻を伏せると 42 対とも完全一致**
⇒ 実内容差分 0 を確認して revert。**生成サイトを追跡している面では、これが非該当の最後の 1 段。**

## 5.16 **「動いたもの」は前タグからの diff で導出する。今日書いた commit の説明ではない**

1.8.32 の予告に「変更は test_tools のみ」と書いた。**当方がその日に書いた commit はそれだけだった**が、
タグ `v1.8.31..v1.8.32` は 6 commit で、うち 1 本（前日にタグ未着のまま積んであった Declares 列の修正）が
document_tools の generator 2 本を変えていた。**受け手 2 レーンが独立に `git log v1.8.31..v1.8.32` で捕まえた。**
両者の判定は自分の import グラフと 2 腕対照で立っていたので外れなかった —— **当方の主張を借りていた面が
在れば「document_tools は 0」と報告して外していた**（受け手の言葉）。

§5.9 は「受け手の起点を知らずに無変更と言うと嘘になる」だった。**送り手の側にも同じ穴がある: 起点は前タグ**であって
「自分が最後に触った記憶」ではない。
```
書く前に撃つ   git diff --stat vA..vB -- . ':!docs'      ← 動いたディレクトリはここから写す
書かない       「変更は X のみ」を記憶から。積んであった commit は記憶に無い
```
⇒ 通知の「動いた場所」節は**この出力を貼るか、そこから写す**。§5.11 の「動いたディレクトリ」の出所はこれ。
**式は差分の言葉で伝えない — 全文を貼る**（1.8.37 の夜）: 「式に `| grep -vic 'warnings found'` を足す」と 3 面に書いたら、旧式 `grep -icE …` にそのまま繋いだ形が

現物は `grep -iE … | grep -vic …`（`-c` は最後に 1 回だけ）で正しかった。受け手の web 面が陽性対照つきで発見 — そして同じ面が
**「壊れていたのは文面から再構成した式で、現物は正しかった」と撤回**（手元に commit 済みの現物があるのに、チャットの文面から再構成して一次資料の欠陥として報告した）。
⇒ 対になる受け手の作法: **手元に現物があるなら文面でなく現物を読む。「この主張の対象は、読んだファイルか、聞いた話か」を送る前に撃つ。** 送り手の「全文を貼る」と対で、片方だけでも防げた。
同じことがコードにも言える: **通知に貼るコマンドや式は、送る時点のファイルから貼る**（1.8.36 の夜、直す前の式を通知に載せ、現物と違った。
受け手が「メッセージでなく現物を採る」と宣言していたので拾えたが、採っていれば最多の綴りを数えない counter を作っていた）。
規約（Agents pack）の変更は SessionStart hook でしか届かず走行中のセッションには来ない — 通知に「`sync-into-project.sh` を手で回す」を 1 行添える。

⚠️ **写すときの数字**: `--stat` の per-file の数（`| 13 ++++-`）は**追加+削除の合計**。「+13/−1」と書きたいなら
`--numstat`（追加・削除が別列）から写す。1.8.33 で `12 / 1` を「+13/−1」と送り、受け手が行数の実測（2,239 → 2,250）で
1 行のずれを検出した。**per-file は `--numstat`、summary 行（`N insertions(+), M deletions(-)`）だけが `--stat` で正しく読める。**
バーは**幅の正規化**もかかる（大きな diff では実数と一致しない）ので、バーの数は読まない（docsite の補足）。
⚠️ 受け手の 1 面も**自分で同じ `--stat` を撃って同じ誤読**をし、通知と一致したので疑わなかった ——
**同じ道具の同じ出力を 2 人が読んだ一致は独立な証拠にならない**。切ったのは別の計器（行数の実測）だった。

### 5.16 追補: 「そちらの sync で動くもの」は**主題の部分集合**ではない（1.8.38）

### 5.16 追補 2: 適用判定は **2 段**で書く —— 「警告が出るか」の前に「変更された経路を通るか」（1.8.39）

1.8.39 の予告は適用判定を「Segment の `items` にオブジェクト要素か binding が在る面」（= 新しい警告が出る面）と書いた。
受け手の web 面が指摘: **require が要るのは converter が「警告する」ときではなく「走る」とき**。Segment を使う面は、
items が全部正しくても変更された converter の行を毎 build 実行する —— 候補 93626ee0（require 欠落）がそのまま配られていれば、
Android を持つ面の `kjui build` は NameError で落ちていた（web は base_converter が core を require しているので落ちない、
と同じ面が後で自己訂正: 「正しい主張に、確かめていない実例を添えると、実例のほうが信じられる」）。
```
A  新しい警告 / 新しい出力が出るか   = 入力の形で決まる（items にオブジェクトが在るか）
B  変更されたコード経路を通るか     = その component / 機能を使っているか（grep -rl '"type": *"Segment"' <layouts>）
```
⇒ **B を先に書く**。B が「はい」の面は A が 0 でも壊れ得るし、判別子（新しい参照が入ったか）を撃つ動機も B から出る。
A だけ書くと、露出 0 の面が「非該当」と自己判定して測らない。

**B は「鎖が走らせるか / 手動か」まで分ける**（1.8.40、受け手の web 面 2 つの指摘）。`jsonui-doc generate html` を「使っている面」と書いたら、
1 面は**手順書に載っているだけで鎖（*.sh / *.yml）からは 0 回**、もう 1 面は `--version` が毎 run 走るだけで変わった経路は通らない、と測ってきた。
鎖が走らせる面は受入がそのまま通過確認になるが、**手動しか無い面は受入で自分が撃たないと版が変わったことに気づけない**。
```
B1  鎖が走らせる   （CI / pretest / scripts に呼び出しがある）→ 受入 = 鎖の緑
B2  手動でしか撃たない（手順書・README だけ）              → 受入で 1 回撃つ、生成物の分母（ページ数 / 指紋）を控える
B3  ロード段だけ通る（`--version` 等）                    → パッケージの import 破綻だけが露出する
```

### 5.16 追補 3: 候補 SHA の更新は**毎回、全宛先へ**（1.8.39）

予告（候補 b571cb74）の後に修正を 1 本同乗させて候補が 93626ee0 に動いたとき、更新を triage 3 レーンにしか送らず、
面レーンには CI 赤の遅延便が初出になった。受け手の web 面: 「(a) 中間の便が届いていない (b) 書き間違い」の 2 択で立て、
実際は **(c) 宛先選択** —— 送り手の意思決定という層が抜けていた。lib 更新レーンは「+3 行だけ」が偽（同乗分の +34/−4 ×4 が載っていない）
と実測で訂正。⇒ 候補が動いたら、**動いた理由・新 SHA・予告候補からの差分の全量**を予告と同じ宛先に送る。
正本はタグ `vX.Y.Z^{commit}`（候補の履歴は受け手の台帳に書かせない）。

## 5.17 **文書が写している文字列**は「動いたもの」の一行 —— ファイル名の表では受け手の写しが古びる

受け手の文書は当方の**文字列**を写している: docsite は `--help` の文面、Agents pack の規約は警告の計数式、
消費側の README は警告の文面（`WARNING [lint-strings]: …`）。列車がその文字列を動かすと、写しは**何も報告せずに**古びる ——
「動いたディレクトリ」の表には `jui_tools/jui_cli/commands/build_cmd.py` としか出ず、受け手はそれが help の文面を変えたと知る術が無い
（1.8.37 の夜、docsite の要請）。§5.16 の diff 導出はファイル名までしか出さない。

⇒ 通知に **「文書が写している文字列」** の行を置く。書くのは (a) 動いた文字列の**種類と現物**（help の文面 / 警告の文面 / 規約の式 / 計数式）、
(b) それが載っている**当方のファイル**、(c) **写しなので出た版で撃ち直す**の 1 句。文字列は差分でなく**全文**（§5.16）。
```
書く   文書が写している文字列: `jui build --lint-strings` の help 1 行（build_cmd.py）、
       binding の警告文面 2 つ（attribute_validator_core.rb）——写している側は出た版で撃ち直す
撃つ   受け手側: grep -rnF '<旧文面>' docs/ README.md   ← 0 なら写していない、1 以上なら更新対象
```
何が「文字列」かは diff で機械的に出ない（help 文・warn 文・docstring の中の式）。**その列車の diff を読んだ人が 1 度だけ名指す**のが
一番安い。名指しが無いと、受け手は全ファイルの全文字列を自分の文書と突き合わせるしかなく、誰もやらない。

### 5.17 追補: 文字列が **ソースの literal か、実行時の合成か** を添える（1.8.39）

1.8.39 の warning 文面 3 種（"is null" / "is an object" / "is an array"）は `"… is #{kind}; items are …"` の**実行時合成**で、
ソースに literal としては存在しない。2 面が独立に「出た版で撃ち直そう」として `grep` で **0 件**を得た —— 1 面は「配布物に 0 件なのに
『陽性対照 OK』を無条件で印字するスクリプト」で危うく docs の 0 を報告し、もう 1 面は仕込み（layout にオブジェクト要素を 1 個挿して
build）で実物を発火させて取った。**探した語がそもそも存在しない語なら、0 は何も意味しない。**
```
書く   文面: `Attribute 'items[1]' in 'Segment' is an object; …`（実行時合成 — literal は `items are string labels` / `dropped from the generated output`）
       ⇒ 受け手は literal 部分で grep、全文が要るなら仕込みで発火させる
書かない 「warning 文面 3 種」だけ（受け手が合成前の断片を知らない）
```
⇒ 文字列を名指すときは **(a) literal か合成か (b) 合成なら grep できる断片** を添える。

## 7.8 予告と bootstrap を同じ応答で撃つと、予告にならない

1.8.32 で予告の送信と bootstrap の起動を同じターンに置いた。受け手（admin backend）:
「**予告が届いた時点で差し替えは既に完了していた**。異議を出す窓としては機能していない」。
⇒ 予告 → **受け手が読める間隔を 1 ターン置く** → bootstrap。予告の価値は時刻ではなく**窓**。

### 7.8 追補: 「窓」は 2 つある。両方の時刻を書く（1.8.33、受け手の web 面 の実測）
```
送り手の窓  bootstrap 完了 → sync 開始            17:43:37 → 17:43:37 = 0 秒
受け手の窓  ~/.jsonui-cli/VERSION が新版 → 受領票（sync-meta）が追いつく   17:38:32 → 17:43:38 = 5 分 06 秒
```
受け手に効くのは**後者**。bootstrap は実体ツリーを先頭の 1 秒で書き終え（VERSION もそこ）、残りは pip / npm。
その間 ①② は新版、④ は旧版 ⇒ 4 点検証は正しく赤だが、**① だけで「更新済み」と読むと vendored 旧版のまま `jui build` が走る**。
⇒ 完了通知には **VERSION が変わった時刻と受領票が動いた時刻の両方**を書く（「bootstrap 17:38:29–17:43:37」は前者の区間）。
受け手側の基準は ④（受領票）に固定するのが正（受け手の web 面 が明文化）。

### 7.8 追補 2: 報告書は受領票の後・完了通知の前に書く —— 予告にそう書く
受け手の 4 点検証の ③（報告書の実在）が **配布直後は 5 版連続で 0 件**（1.8.15〜1.8.33、受け手の web 面）。
受け手は bootstrap の着地を自分で検知して受入を始めるので、**報告書はまだ無い**（順序: bootstrap → sync → 受領票 → 報告書 → 通知）。
5 回とも全鎖の後に撃ち直せば引けている＝欠陥ではなく順序。⇒ **予告に 1 行**:
「報告書 §N は受領票確認の後・完了通知の前に書く（bootstrap 着地時点では未作成）」。
完了通知には**報告書 §N を書いた時刻を秒で**（「19:0x」と丸めると受け手の mtime 観測と食い違って見える — 1.8.35）。
報告書は通知の後も**受入からの追補で書き換わる**ので、「以後の書き込みは追補」と添える。SHA で引く ③ が確定するのは「その時点の本文」まで。

### 7.8 追補 3: 予告の時刻は**床**。早く緑になっても待つ（1.8.34）
「早くて 18:55 頃」と書いて、CI が早く緑になったので 18:21 に撃った。受け手（web 面）は「18:55 まではフルスイートを回さない」と
判断していて、**コミット 18:21:34 / 境界 18:21:43 の 9 秒差で助かった**。「早くて」を下界として使う受け手に対し、
**下界が 33 分外れる予告は、予告が無いより悪い**（安全な窓があると誤認させる）。
⇒ 予告に書く時刻は **「この時刻より前には撃たない」の床** — CI が先に緑でも床まで待つ。床の前に撃ちたければ**予告を出し直す**。
加えて **bootstrap の直前に 1 行**（「いま撃ちます」）— 長い run を持つ面がそこで止められる。
