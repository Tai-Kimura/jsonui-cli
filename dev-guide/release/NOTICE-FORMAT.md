# 配布通知の書式

**なぜこのファイルが在るか。** 2026-09-01、v1.7.52 の告知で 2 件の誤りを 7 面へ
配った。うち 1 件（`validate` の呼び方）は、**v1.7.50 の報告書で私自身が 3 段に
整理した内容**を使わなかったもの。⇒ **報告書に書いた整理が、次の告知に反映される
経路が無かった。** このファイルがその経路。**告知を書く前に必ず読む。**

---

## 1. 行ごとに出所を書く

```
[撃った] その場でコマンドを実行して得た値
[読んだ] 実装を読んで得た値（行番号を添える）
[導いた] 上の 2 つから推論した値   ← ⚠️ 最も誤りやすい
```

⚠️ **v1.7.52 の 2 件はどちらも [導いた] を [読んだ] のように書いた。**

- 「`headers` を書くと error」← 語彙からの削除**意図**から導いた。実際は
  warning / exit 0。**同じ diff に `errors.append` の実例が 3 つ、
  `result.errors == []` を固定したテストまで在った**
- 「`validate` 引数なしで全件」← 全件を撃つ**意図**から導いた。実際は exit 2。
  **`--help` を 1 行読めば分かった**

⇒ **[導いた] と書けない行は、書く前に撃つか読む。**

**もう 1 本、受け手側の軸がある: その行は誰が再検証できるか。**
[撃った/読んだ/導いた] は書き手の分類で、受け手が要るのは
**「自分の面で撃てるか」**。⚠️ 値は受け手ごとに変わるので、
**「撃てない」ではなく「どの面なら撃てるか」を書く** ——
そして**送り手のその見立ては保守的に外れる**。生成器の挙動は「生成する面」で
なくても撃てる（要るのはプロジェクトではなく fixture）。本当に面が要るのは
**ランタイム挙動**（iPad の size class の類）だけ。ある面は「撃てない」と
書かれた生成器の主張を fixture で 2 版比較し、引用ではなく実測で掲載した —
受け手が「撃てない」を確かめずに引用へ倒すと、撃てたはずの主張が
引用のまま残る。⇒ 書くのは「どの面なら」に加えて**「何が要るか」**
（fixture で足りる / ランタイムが要る）。 ある面はこれで
「実測として書かず、宣言の言葉として引用する」という掲載判断ができた。
「撃てない」とだけ書かれていたら、引用すべきか落とすべきか決められなかった、
という報告つき。

**新属性の告知にはもう 1 行**: 「受け手側に属性名 → 出力先の**手書き対応表**が
無いか」。ある面では手書きの category map に無い属性が**どのカテゴリにも一致せず
緑のまま publish されない**形で、SSoT が宣言した属性が 21 日間どこにも
掲載されなかった（兄弟属性が在ったから不在が読めただけで、単独なら
気づく手段が無かった、と当人の実測）。

⚠️ **出所の明記は「借りる量を減らす」だけで、借りる構造は消えない**（lib レーン）。
clone を持たない純粋な消費機は結論を借りるしかない。⇒ **各行を、その面で
版をまたがず検算できる性質として書く**のが上位の形。

## 2. 結論ではなく性質を配る。ただし判定が閉じるかを見る

```
✗ 結論   「警告 1 行を見落とせば気づかないまま書き続けられます」  ← 借りるしかない
△ 性質①  「気づけるかは Warnings: の基準値が 0 かで決まる」        ← 閉じていない
✓ 性質①∧② 「気づけるのは、基準値を次回と突き合わせる装置がある面だけ。
            基準値が 0 か非 0 かは、装置が在る面での感度の話」
```

⚠️ **配る性質が、それだけで判定を閉じるかを見る。** 閉じない性質は
**「確かめた気になる性質」**になり、②を欠く面が「自分は①だから安全」と読む。
**判定を分けているのは②（装置の有無）だけ。**

## 3. 段を配るときは、軸を名乗る

⚠️ **v1.7.52 で 2 つの軸を 1 本の梯子に混ぜた。** 混ぜると、
**手順を変えた瞬間に段が変わる面**（＝ほとんどの面）が固定属性として引用される。

**軸 A — 面が構造的に該当しうるか**（v1.7.50 台帳の軸）

| 段 | 成立させるもの | 忘れたら |
|---|---|---|
| 強（構造） | config が `test.install` を宣言していない ⇒ `resolve_targets` が空 | **打ち忘れが存在しない** |
| 中（手順） | `test.install.src` ちょうどを渡す | 黙って危険側へ落ちる |
| 弱 | ディレクトリを渡している | **理由にならない**（部分ディレクトリも同じ形で壊れる） |

**軸 B — 呼び方の安全度**

| | |
|---|---|
| `--no-install` | ⚠️ **手順**。毎回打つ必要があり、忘れれば静かに危険側へ戻る |
| 引数を部分集合に絞る | 軸 A が「強」でなければ危険 |

🚨 **軸 B は「安全度の順」であって「置換可能な選択肢」ではない。**

`--no-install` は `Validate only; skip flatten-install even if test.install is
configured`（`--help`）。⇒ **install を必要とする面にとっては別の操作。**
平坦化された `.test.json` を読む UI テストを持つ面が `--no-install` に寄せると、
**テストが 0 件になるのではなく、前回の内容で緑になる。**

⇒ **軸 B を告知に載せるなら「`--no-install` へ降りると install が止まる」を必ず併記する。**

⚠️ **この規則は、このファイルの初版が配られた当日に、ある面が撃って見つけた。**
初版は 3 段を「安全度の梯子」として並べており、**梯子は上に登れることを含意する。**
含意まで書かないと、規則そのものが誤指示になる。

📌 **同じ効果を出す 2 つを並べたら、忘れたときに何が起きるかで分ける。**
`--no-install` と「config に宣言が無い」はどちらも `resolve_targets` を空にするが、
**前者は覚えている必要があり、後者はリポジトリの状態**。

⚠️ **段は面の属性ではなく、面と時点の関数。** 聞くなら
**「あなたはどの段ですか」ではなく「今どれが成立していますか」。**
前者だと受け手が固定属性として答える。

## 4. 露出列には分母と対照を書く

```
scenarios を持つファイル : 886
シナリオ                 : 3861
対照 'status' が在る     : 3861   ← 網が生きていることの対照
対照 'body' が在る       : 3828
'headers' が在る         : 0
```

⚠️ **対照は測定と違う道具で撃つ。** 同じ walker を通すと欠陥を共有する
（`grep` の shim が `.gitignore` を honour して 78% を不可視にしたとき、
対照も同じフィルタを通って一致して見えた）。

⚠️ **走査根を書く。** v1.7.52 で commit 本文の `1189 files` と面の分母 `886` が
食い違って見えた。実際は `886 + 302(ツール側 fixture) + 1 = 1189` で
1 も違わず閉じていた。**食い違いではなく、根が違うだけだった。**

## 5. 範囲の起点を書く

```
✗ 「SHA 945d4fd0…」だけ        → 受け手が tip を撃って「主張と違う」と読む
✓ 「範囲: v1.7.51..v1.7.52（起点タグ → タグ、6 commits）」

⚠️ **SHA はコミット SHA（`^{commit}` 解決済み）と明記する。** 注釈付きタグでは
`git rev-parse vX.Y.Z` がタグオブジェクトを返し、受け手が SOURCE_SHA と
突き合わせると**正しい版で偽の不一致**が出る（2 レーンが同日に踏んだ）。
```

タグ先の commit 単体は 1 ファイル 12 行、範囲は 15 ファイル。**別物。**

⚠️ **タグは CI 緑を実測した commit に打つ — 「release: x.y.z」commit と一致するとは
限らない。** release commit で CI が赤になれば後続 fix にタグが載る（v1.7.52 / v1.7.53）。
一致している版（v1.7.54 / v1.8.0）は結果であって規則ではない。受け手が「タグが
release commit の後ろにある = 動かされた」と読む前に、タグ先の `VERSION` と報告書の
SHA を見る（backend レーンが 4 版まとめ検証で問うた）。

## 5.5 変更は**絶対座標**で書く。差分で書くと、受け手が居ない版を仮定する

⚠️ **告知の宛先は版を持っている。そして送り手はその版を知らない**（面は自分で pin する）。
⇒ **差分で書くと、受け手は「自分に当たるか」を判定するために、送り手が仮定した起点に
自分が居ることを確かめねばならない。その材料は告知の中に無い。**

**実例（2026-09-04、列車の誤り #63）**: ios driver の stderr 変更を **「1.9.8 → 1.9.9 の差分」**として告知した。
受け手の面は **1.9.6** に居り、その面が文字列一致で見ていた文
`scrolled both ways and it is still off the viewport` は **1.9.4〜1.9.7 に実在して 1.9.8 で削除**されていた。
⇒ **告知が名指した区間の外に、その面の実害があった。** 面の集計は 4 パターン中 2 つが
同時に 0 になるところで、**「起きなかった」と読める形**だった。

```
✗ 差分で書く
   「1.9.8 → 1.9.9 で末尾が `that viewport` → `that visible part` に変わりました」
   受け手が 1.9.6 なら、この 2 版のどちらにも自分は居ない

✓ 絶対座標で書く（版ごとの実物を並べる）
   1.9.4 – 1.9.7  "... scrolled both ways and it is still off the viewport"
   1.9.8          その文を削除、"still not hittable" に統合
   1.9.9 – 現行   "... visible part of it <rect> ...; hit point inside|OUTSIDE that visible part"
```

**送り手側の自己検査**（受け手レーンの定式、そのまま採用）:
> **受け手が版 X に居るとき、この告知のどの行を読めばよいかを、2 つ以上の X について
> 自分で答えられるか。** 答えられなければ、まだ絶対座標になっていない。

**表の作り方**（文字列がどのタグ区間に在ったかを撃つ）:
```bash
# ⚠️ 件数ではなく**行を出す**。理由は下
for t in $(git tag --list | sort -V); do
  echo "--- $t"
  git grep -n "<文字列>" "$t" -- Sources/ 2>/dev/null
done
```
⚠️ **件数だけ数えると、コメントと出力を区別できない。** この recipe を書いた直後に
自分で踏んだ: `still off the viewport` を数えると **1.9.8 = 0 / 1.9.9 = 0 / 1.9.11 = 1** と出て、
**その文が復活したように読める**。実体は **1.9.11 の doc comment がその文を引用している**だけで、
出力には無い（引用したのは、まさにこの事例を説明するため）。
⇒ **行を見れば `///` で始まっているのが分かる。件数では分からない。**
[[feedback_one_hit_is_more_dangerous_than_zero]] の形そのもの。

## 5.6 bootstrap が**複数版を飛び越す**なら、載る版を名指す

⚠️ 予告と受け手の実行の間に版が進む。**2026-09-04、2 レーンが独立に踏んだ** ——
告知は 1.8.21 のものだったが、両レーンが撃った時点のディスクは **1.8.23** だった。
どちらも**自分の span を取り直して**検算したので実害は出ていないが、
**予告の span をそのまま検算に使う受け手は、間に挟まった版を見ないまま
「刻印のみ」を確認したことになる。**

⇒ 告知に**この配布後に `~/.jsonui-cli/VERSION` が何になるか**を書く。
受け手は自分の出発点とのズレをその場で見つけられる。

## 5.7 「この配布で **sync が触る面**」を書く。ただし**面の側で測る**

受け手が自分の tree の差分と突き合わせられる形にする。⚠️ **その内訳は
リポジトリ側の diff からではなく、面が実際に vendor している物から作る。**

**実例（列車の誤り #66）**: 「版スタンプ 5 ファイル（sjui / kjui / rjui / test_tools / document_tools）」
と書いたが、**面は 3 または 1** だった —— **test_tools と document_tools はどの面にも
vendor されていない**（bootstrap 経由）。5 は `git diff --stat -- <tool subtrees>` の値、
すなわち**リポジトリ側の数**。⚠️ **同じ報告書の数時間前の節に「面は test_tools を
vendor していない（実測 0 コピー）」と自分で書いてあった。**

```bash
# 面ごとの実測（リポジトリ側の diff ではなく）
for t in sjui_tools kjui_tools rjui_tools test_tools document_tools; do
  find <face> -maxdepth 3 -type d -name "$t" -not -path "*/node_modules/*"
done
```

⚠️ **併せて「変わらないはずのもの」を書く。** 受け手が `jui build` の diff 0 を
**予測の的中**として読めるようになる —— 何も知らずに 0 を見れば「今回は何も無かった」で
終わる（受け手レーンの定式）。**自分が測った範囲と測っていない範囲も名乗る**:
「ソースを読んだだけで、そちらの面に対しては測っていない」と書くと、
**受け手が自分を唯一の反証手段だと理解して撃つ。**

## 6. 配布時刻を書く — `date -u` の出力をそのまま貼る

⚠️ **手で書き直さない。** v1.7.53 で JST の数字に Z を貼って配った（実測 10:12Z を
「19:12Z」と表記）。時刻を残す運用は受け手の照合に使われるので、**単位が偽なら
値が正しくても台無しになる。** 受け手側の言い方では「検査の件数は単位と分母を
名乗る」の単位側の違反。

⚠️ **計器の部分出力も合成を誘発する。** v2.24.0 で watcher に `date -u '+%H:%M:%S'`
（時刻のみ）を印字させ、通知作成時に **UTC の時刻へ JST の日付**を貼った
（「19:12Z」は時刻の単位が偽、今回は日付の出所が偽 — 同じ欠陥クラスの別の綴り。
受け手レーンの照合が検出）。**watcher・ポーリングスクリプトにも `date -u` をフル出力で
印字させ、通知はその行を貼るだけにする。** 欠けた部分を後から手で補うくらいなら、
計器を直してから撃ち直す。

2 件は同じ癖の別の綴り: **2 つの時計の読みを 1 つの文字列に組み立てている**
（JST の数字 + Z / UTC の時刻 + JST の日付）。組み立てる限り、正しい半分が
誤った半分をもっともらしく見せるので、受け手は照合する動機を持たない。
閉じ方は逐語貼り付けのみ — **組み立てた時刻はどれほど自然に見えても出さない。**

⚠️ **時刻を照合する側も、読んだフィールドを名乗る。** commit 日時（`%ci`）と
タグ日時は別のフィールドで両方真になり得る — 食い違いは「相手の誤記」と
「こちらの欄違い」の**両方が予測する**ので、どちらを読んだか言わない照合は
所見にならない（受け手レーンの near-miss 開示より）。

**配布は自動、受入は手動。** ⇒ `bootstrap` と `jui sync_tool` は、
**他レーンが実験を回している最中に計器を差し替える。**
v1.7.52 で、ある面の E2E 実験の腕をまたいで `jsonui-test` が入れ替わり、
**2×2 の 1 ラン分が無効になった**（本人申告: 確認要請が無ければ
腕 D の 3/24 を CPU 60 倍の効果として報告していた）。

⇒ **通知に配布時刻を書く。** 受け手が自分の計測の時刻と突き合わせられるように。

## 7. 観察を書くなら、それを撃つコマンドを添える

⚠️ **繋げた部分が「指示の形」か「観察の形」かで、検算される確率が違う。**
指示は撃たれるので同日に検算される。**観察は撃つ動機が無いので、
誤っていても台帳に載ったまま残る。**

⇒ **撃てない観察は書かない。書くなら撃つ手順を添える。**

🚨 **添えるのは「測った部分を再現するコマンド」ではなく「繋げた部分を反証しに行く
コマンド」。** 前者は必ず成功するので、**添えるとかえって信頼を上げる。**

実例（ある面の自己申告）。観察「複製が古い ⇒ エディタ緑 → validate 赤が作れる」に:

```
✗ cat .mock.schema.json | grep headers   → 観察が偽でも「複製は古い」が返る。
                                            繋げた部分は検算されないまま通る
✓ jsonui-test validate <targets>         → PASSED が返り、繋げた部分が偽だと分かる
                                            （実際 warning / exit 0 だった）
```

⇒ **添えるコマンドが「その観察が偽だったら別の答えを返す」形になっているかを見る。**

## 7.5 「無かった」と「見ていない」を書き分ける

⚠️ **通知の欠落は、受け手からは「変更が無かったこと」と区別できない。**（消費側レーンの
定式、2026-09-03）。⇒ ある面について何も書かなければ、受け手は「そこは動かなかった」と
読む。実際には**測っていない**だけかもしれない。

```
✗ （何も書かない）                 → 受け手は「動かなかった」と読む
✗ 「当方の把握では 0 件」          → 把握は測定ではない。何を見たか言っていない
✓ 「help が動いた葉: 0 件（58 葉を比較）」      ← 測った
✓ 「help の変化は測っていない」                 ← 測っていないと言った
```

実例: `jui build --lint-strings` は不変条件 #4（localize ゲート）をビルドに載せる唯一の
フラグだが、それを足した列車の通知に**葉の粒度の記載が無く**、ドキュメント側は未掲載の
まま 4 か月生き延びた。当時その運用が無かったのが理由だが、**受け手にはその区別が付かない**。

⇒ **変更駆動の運用（受け手が「動いた面」を読んで追随する）を敷いた以上、動かなかったことも
測って書く**。書けないなら「測っていない」と書く。**沈黙は第三の値であって、0 ではない。**

## 7.6 緊急通知は「撃つな」で書く。「版を戻せ」は実行できない

⚠️ **`~/.jsonui-cli` はマシン共有で、配布は上書き。** 消費側に**版を選ぶ手段は無い** ——
ある面が戻せば他の全レーンに効く。⇒ **「1.8.5 のままで作業してください」は、受け手が
実行できない指示**（受け手はそれを試み、共有資源なので動かせないと知る）。

```
✗ 「1.8.5 に留まってください」        → 実行不能。しかも実行しようとすると他面を壊す
✓ 「`jui build` を撃たないでください」 → 受け手が単独で実行できる
✓ 「壊れているのは `jui build` だけ。`verify` / `validate` は無事」  ← 残る道を名指し
```

⇒ **緊急通知の単位はコマンドであって版ではない。** 版で条件を出すと、受け手は版を
動かそうとする。あわせて**戻し方があるなら明示する**（無いなら「無い」と書く —— ある面が
「戻し方が無いなら無いと書いてほしい」と要請した）。

⚠️ **壊れたコマンドが残す痕跡も書く。** 1.8.6 の crash は正規化の**手前**で落ちるので、
`Layouts/Resources/colors.json` が SSoT のフラット形のまま配られ、**モード構造が剥がれた
「別の正しい形に見えるファイル」**が残った。⇒ `git status` の行数でも目視でも異常に
見えない。**「中途半端なツリーが残る」だけでは受け手は探せない。何がどう変わるかを書く。**

## 7.7 配布の前に窓を聞く。ただし 2 択に畳まない

⚠️ **配布は 1 秒で終わるが、それが壊す窓は数分〜数十分ある。** `bootstrap` と `sync_tool` は
他レーンが計測している最中に計器を差し替える（v1.7.52 で E2E 実験の 1 ラン、2026-09-02 に
deploy 中の `jui build` が版をまたいだ）。⇒ **配布の前に、窓を開けている可能性のある相手へ
1 行入れる。**

**聞き方が答えの質を決める**:
```
✗ 「配布して良いですか / 待ちますか」
   → 受け手が「待つと悪化する」ケースで**例外を説明する**必要が出る（実際に起きた:
     壊れた版のせいで相手の窓は配布でしか閉じられなかった）
✓ 「この配布はあなたの窓を壊しますか、閉じますか」
   → 一語で答えられ、しかも答えが正しくなる
```

⚠️ **ただし 2 択に畳んだ時点で第 3 の形が落ちる。** 実際に返ってきた 3 つ目は
**「今は壊すが、自分で閉じられるので待てる」**だった（前回は相手に窓を閉じる手段が無く、
今回は在った ＝ **同じ質問への正しい答えが状況で変わる**）。⇒ **2 択で答えられないときは
答えの形のほうを言ってよい**と明示して聞く。

## 8. 宛先は受領票から作る

⚠️ **名乗りベースで宛先表を作ると、名乗らなかった面が静かに消える。**
2026-09-01、ある面が表から落ち、
**受領票は 3 版とも正しく更新されていたのに、v1.7.49〜51 の通知が未着だった。**

```
find <consumer roots> -name sync-meta.json -path "*/.jsonui-cli/*"
```

**この出力（受領票の実在）と宛先表を、双方向で突き合わせる。**
逆向き（宛先表に無いが受領票が在る）が「配っているが誰も読んでいない面」を拾う。

## 5.8 **追記した節にも SHA を書く**（受け手は報告書を SHA で引く）

2026-09-04、ある面の 4 点照合が **3/4** で止まった:
```
1 VERSION / SOURCE_SHA   OK
2 tag → commit SHA       OK
3 報告書                 ❌ grep -l '<sha>' docs/bugs/reports/*.md → 0 件
4 --version / sync-meta   OK
```
**報告書は実在し、告知が指した節も実在した。入っていなかったのは SHA。**

⇒ **既存の報告書に `## N. 追補: X.Y.Z` として節を足す形式は、
受け手の「SHA で引く」手順を構造的に落とす。** ファイル名は前の版のままなので、
**ファイル名でも引けない。**

**書き方**: 追補の節は見出しの直後に必ず
```
tag vX.Y.Z → commit <40 桁の ^{commit} 解決済み SHA>
```
⚠️ **その面はこの前に「報告書が無い」を 2 回観測しており（1.8.7 / 1.8.15 は未執筆）、
今回は「在るが SHA が無い」。同じ症状・別の原因**。
**原因を確かめてから書いた**と明記してきた ⇒ こちらも症状ではなく原因ごとに直す。

## 5.9 **「挙動変更なし」は差分の主張。区間を書かないと嘘になる**

§5.5 は「変更は絶対座標で」。**その裏面が「変更が無い」の主張**で、
こちらのほうが踏みやすい —— **無変更は絶対座標で書けない**（区間の性質だから）。

2026-09-04 の実例。1.8.28 の告知に「順序ガードを追加（**内部テストのみ、挙動変更なし**）」と書いた。
```
[実測] 生成器の差分 v1.8.27..v1.8.28   空          ← 主張は 1.8.27 起点では真
[実測] 生成器の差分 v1.8.26..v1.8.28   +70 −13     ← 受け手は 1.8.26 に居た
```
⇒ 受け手の面では **`branch-check-ios` が 18 stale / 1 drifted** になり、
**再生成すると生成ランタイムが 1 本、冪等性という挙動の性質ごと変わった。**
**「内部テストのみ」はライブラリについては真、消費側の生成物については偽。**

📌 受け手の定式（採用）: **「vendored 不変を生成器不変の根拠にしない」の兄弟 ——
「内部テストのみ」を生成物不変の根拠にしない。**
⇒ **告知が挙動不変と言っても、`--check` は撃つ。**

**書き方**: 無変更の主張には**必ず区間**を添え、**跨ぐ受け手が居ることを前提にする**。
```
✗ 「挙動変更なし」
✓ 「v1.8.27 → v1.8.28 では生成物に差分なし（実測）。
    ⚠️ 1.8.26 以前から上げる面は 1.8.27 のランタイム変更を含むので `--check` を撃つ」
```
⚠️ **これは 2 度目**（v1.9.8→1.9.9 の stderr 変更を 1.9.6 の面に語った件と同型）。
**1 度目は「区間の外に害が在った」、2 度目は「区間の外に変更が在った」。**
**同じ穴の 2 つの向き。**

## 5.10 **受け手に指定する確認コマンドは、受け手の面で判別するか**

同日、非該当かもしれない面へ「`--check` を撃ち直してください」と書いた。
**その事案の核心は「`--check` の出力が『宣言なし』と『読まれていない』を区別しない」こと**だった。
⇒ **指定した計器は、指定した相手の面では原理的に判別しない。**

受け手はこちらの指定を採らず、**ソースを数えた**:
```
subSpecs を持つ spec      0
unitContracts を持つ spec 0
（対照）branchContracts   18   ← 走査が生きている確認
```
⇒ **判別したのはソース側の 0。**「撃つ代わりに数えた」（受け手の言葉）。

⚠️ 別の面は**両方**撃ち、**grep の 0 と道具の `0 carrying` の一致**で閉じた ——
**「grep の 0 を信用しない」を理由に挙げている**。⇒ どちらも正しく、**軸が違う**。
**書き方**: 確認手順を指定するときは
**「その出力が、該当と非該当で違う値になるか」**を先に自分で確かめる。
ならないなら、**判別する別の計器（ソースを数える）を書く**。
