# 配布前スモーク — 腕の一覧と、誰が撃てるか

配布の直前に撃つ。**6 スイートの緑も CI の緑も、ここで落ちる欠陥を通した実績がある**
（1.8.6 は全消費者の `jui build` を壊し、1.8.10 候補は移行したエントリを再刻印した。
どちらもスイート緑・CI 緑）。

## 表の読み方

**捨てプロジェクトで撃てる腕は多い。** `jui init --project-name X --web ./web` は
**Xcode も Gradle も要らず、実 build が exit 0 で通る**（実測: 14 tracked）。⇒ **manifest 周りの
腕はここで全部撃てる**（記録・churn・`dropped`・キー衝突の警告行まで、**エントリを人為的に
仕込んで発火させられる**）。**他レーンの木を借りずに済む。**

⚠️ **かつてこの表には「列車は分母を作れない」と書いてあった。偽だった** —— `--ios ./ios
--android ./android` で失敗したのを、**プラットフォーム全般の制約と一般化していた**。
**1 通りで失敗して「できない」と書いた。**

**それでも列車が撃てない腕は残る**: 実 iOS / Android のツールチェーンが要るもの、
**消費側のゲート・基準値装置との相互作用**、**その面の実データ**（合成では綴りも版も件数も
自分で決めてしまうので、**自分の仮説を確かめるだけになる**）。
⇒ **撃てない腕は消費レーンに依頼する。省略しない。** 依頼は事前に断り、撤収まで手順に含める。

⚠️ **この列は測ってから書くこと。** 一度は「列車は分母を作れない」と書き、一度は撃てる腕を
「実面」に振っていた。**どちらも撃たずに書いた。**

## ⚠️ 走ったコードの判別 — 版名は判別子にならない

`JSONUI_CLI_PATH` を立てても**走るコードは変わらない**。`jui` のランチャは
`Path(__file__).resolve().parent.parent` を `sys.path` に入れる、つまり**自分の置き場所**から
解決する。あの環境変数は `sync_tool` の**出所**にしか効かない。

```
dev 版を撃つ:   <worktree>/jui_tools/bin/jui build
```

そして **worktree の `VERSION` は未 bump なので、`--version` は前の版を名乗る**。
⇒ **版名では区別できない。そのリリースだけが持つフィールドの有無を判別子にする。**

```
python3 -c "import json; d=json.load(open('.jsonui-cli/generation-manifest.json')); print('trackedByDirectory' in d.get('summary',{}))"
```

実例: 列車は `JSONUI_CLI_PATH=<worktree> jui build` を撃ち、**dev 版を測ったつもりで前の
リリースを測っていた**。気づいたのは判別子が無かったからで、出力そのものは正常に見えていた。

## ⚠️ 部品を単体で撃つ検算は、順序が原因の欠陥を見られない

列車は移行関数を実データ 786 件に当てて「537/537・249/249、刻印は 1.8.7 のまま」を得た。
**版まで見ていた。それでも通った** —— 撃ったのが移行と prune だけで、`written()` との
相互作用を再現していなかったから。実際の build では `written()` が先に走り、その結果が
移行後のエントリを上書きする。

⇒ **単体で緑 → 実面で赤、は 1.8.8 の窓バグと同じ形**（順序が原因、fixture が順序を表現して
いない）。**検算の側で同じ形を繰り返さないこと。**

## 期待値は、測る前に固定する

依頼した腕の期待値を**依頼の時点で書き出す**。⇒ **結果を見てから「まあ妥当」と読まないため。**
⚠️ **1 人の事前登録では弱い**（自分の仮説を知っている）。**依頼側と実測側が独立に書く**と、
算術が一致したことが証拠になる。

⚠️ **条件はエントリ丸ごとで書く。** 「version が一致」だけだと、**version は保つが `generatedAt`
は現在時刻で上書き**という直し方が緑で通る。実例として、再刻印の修正の期待値はこう固定した:
```
wrote 310 of 508            （508 − 198。依頼側と実測側の算術が独立に一致）
移行 198 件の version        1.8.7 のまま
移行 198 件の generatedAt    18:21:35Z のまま   ← version だけ見ると見落とす
```

## 撤収

実面を借りたら、**借りた側が元に戻す**。manifest を `git checkout` で戻し、生成物の差分 0 と
ゲート緑を確認するところまでが手順。

⚠️ **manifest だけでは足りない。`jui build` は vendored ツールの版も書く**ので、**未リリースの
版がツリーに刻まれる**。⇒ **列挙で守らないこと。列挙は漏れる。差分は漏れない**:

```
probe 前:  git status --short --untracked-files=all を記録 + 追跡外のファイルを cp 退避
probe:     撃つ
probe 後:  git status の差分を取り、増えた分を全部復元
           （tracked は git checkout、untracked は cp 戻し）→ 記録した状態と一致するまで確認
```

⚠️ **何個あるかは面によって違う**（web 単一面には sjui / kjui の `version.rb` が無い）。
**そして次の版で 1 つ増える**（`generation-manifest.json` は 1.8.6 で増えたばかり）。
⇒ **数を配るのではなく「差分で取れ」を配る。**

⚠️ **分母を数えるときの罠**: `manifest` という語で探すと、Next.js の面では
`.next/**/*-manifest.json` が数百件出る。**フレームワークの成果物が圧倒的多数**になる。
⚠️ **生成物そのものが増えることもある** —— 入力（swagger 等）が窓の前に動いていると、
**未リリース版が新しいファイルを作る**。実例: red-check の最中に 24 本 / 54 本の新規生成物が
出たが、原因は版ではなく backend の schema が 283 → 298 に増えていたこと。
⇒ **撤収時は「差分 0」ではなく「窓の前と完全一致」で確認する**（新規ファイルは diff に出ない）。

**由来**: これは丁寧さではなく事故の産物。共有ツリーに囮を置いたまま去り、**他レーンを 40 分
誤診させた**。そこから「置く直前と撤去直後に一報」「重い run も同じ」「一報の中身は
**止めてくれ**ではなく**時刻を記録してくれ**」が足された。⚠️ 列車も一度、他レーンの作業ツリーで
スモークを撃ち、**pin と刻印が食い違う状態を残していった**（測定のつもりで書き込みをしていた）。

## 窓を聞く — 分母を自分の手順に当てる

**1 面の許可を、全面に聞いたことにしない。** 実例: 1.8.11 の配布で、列車は 1 面から
「配って構いません」を得て配布した。⚠️ **別の 1 面は先行実測の最中で、そう申告していた。**
⇒ その面は `~/.jsonui-cli` から同期して vendored 刻印が pin から外れた。

📌 **1.8.9 のときは「聞くのを忘れた」、1.8.11 は「1 面に聞いて済ませた」。**
⚠️ **後者のほうが悪い** —— **手順を踏んだ形が残るので、踏んでいないことが見えない。**

⇒ **聞いた面と返答を数える。** 返答が揃わない面があるなら、**配布を待つか、その面に
「いま配る」と名指しで伝える**。⚠️ **返答が無いことは「窓が閉じている」ではない。**

## 掃きは「保持 / parse / 引用」の 3 分類で

出力の文言を変える前に、消費側の読み手を掃く。⚠️ **「基準値に保持しているか」だけでは
足りない**:

```
保持   基準値ファイルに焼かれている       → 文言が変わると CHANGED で鳴る（気づける）
parse  正規表現で値を抜いている           → 変わると空を返す。⚠️ 空が正常に見える（気づけない）
引用   ドキュメントや手順書が文字列を含む → 鳴る仕組みが無い（誰も気づかない）
```
実例: ある面は「成功行は読んでいない」と考えていたが、**報告用に parse していた**箇所が
実在し、ブロックの分割で空を返すようになった。⇒ **保持と parse は別の読み方で、
parse のほうが壊れ方が静か。**

⚠️ **掃きには分母を印字させる**（何リポ・何ファイルを走査したか、実在確認、陽性対照）。
実例: 掃きが全パターン 0 件を返したが、原因は `$FACES` が語分割されずリポ名の連結を
1 パスとして渡していたこと。**陽性対照が計器の故障を捕まえた。**

## 直したら、その場で兄弟を掃く — そして掃いた結果も書く

**修正の直後に、同じ形が他に無いかを掃く。** 指摘されてからでは 1 リリース遅れる。
実例: help カードの誤文を 1 枚直したが**同じ文を持つ兄弟カードを見に行かず**、次の版で
列が引いて発覚した。

⚠️ **掃いた結果を、0 件でも記録に残す。** 理由が非対称:

```
修正        commit・台帳・刻印の 3 箇所に痕跡が残る
掃いた隣    何も残らない
⇒ 後から「1 件直した」が「その族は点検した」に見える
```

⇒ **「直した記録は残るが、直さなかった隣は記録に残らない。」** 掃いて 0 件だったことを
書いておけば、**点検の範囲が痕跡になる**。

📌 これは列車側の「1 面に聞いて全面に聞いたことにした」と同じ形 ——
**手順を踏んだ形が残るぶん、踏んでいない範囲が見えない。**

## ⚠️ 捨てプロジェクトは、配布が結線されていない（1.8.12 で解消）

**1.8.12 以降の `jui init` は `layoutsDir` を書く**（実測: `{"web": {"root": "./web",
"layoutsDir": "src/Layouts"}}`）。⇒ **以下は 1.8.11 以前の bed について**。
⚠️ **節ごと消さないのは、判別子の誤読とその由来がここにしか残っていないから。**

1.8.11 以前の `jui init` が書く config には **`layoutsDir` が無い**（実測: `platforms: {"web": {"root": "./web"}}`）。
配布側は `layouts_rel = pconfig.get("layoutsDir")` が空なら黙って `continue` する。
⇒ **SSoT を編集しても face に届かず、届かなかったことも言われない。**

🚨 **この節は一度「判別子は成功行にある」と書いた。不健全だった。** `(N file(s) distributed
in total)` の**欠落は 3 通りに読める**:

```
_distributed_file_count()   except OSError: return None        ← 数えられなかった
                            return total or None               ← 本物の 0 も None になる
coverage_line()             if distributed is not None and distributed != total:
                                                               ← tracked と一致しても出ない
```
⇒ **「数えられなかった」「0 だった」「tracked と同数だった」が同じ沈黙になる。**
📌 **「不在は測定結果」と言い続けた波で、不在に 1 つの意味を与えて手順書に書いた。**

⇒ **健全な判別子は config を直接読むこと**:
```
python3 -c "import json; d=json.load(open('jui.config.json'));
print([k for k,v in (d.get('platforms') or {}).items() if 'layoutsDir' in v])"
```
⚠️ **そして結線しただけでは足りない** —— `layoutsDir` を足すと、**SSoT 側に layout が 1 つも
無い面では配布の prune が face の layout を消す**（仕様どおり）。⇒ **走査対象が無くなるので、
色を参照する layout が 1 つも無い状態になり、colors は schema に関係なく生成物に届かない。**
⇒ **SSoT 側に layout を置いてから撃つ。**

**由来（この節が一度書いた誤りを、印を付けて残す）**:
```
generation manifest: 14 tracked generated file(s) as 1.8.11
                     ↑ (N file(s) distributed in total) が無い
❌ 「= 配布 0 件」と読んだ。3 通りに読めるので偽
```
⚠️ **列車はこの欠落を見て「0 distributed だろう」と説明で片付け、その条件のまま
「読めない入力に固有」という対照を取った。対照は無効だった。** そして**その誤読を
判別子として手順書に書いた**。⇒ **削除せず残すのは、次の読み手が同じ読みを再発明しないため。**

**腕ごとの依存**: manifest だけを見る腕（記録・churn・`dropped`・衝突）は結線に依存しない。
**配布・SSoT・colors を経由する腕は依存する** —— しかも依存の段が 3 つある
（`layoutsDir` が在るか / SSoT 側に layout が在るか / その layout が色を参照するか）。

## ⚠️ bed の vendored ツールは、インストール済みコピー由来

`jui init` は各面の `*_tools/` を **`~/.jsonui-cli` から**ベンダーする。⇒ **worktree の
`bin/jui` で init しても、Ruby 側（sjui / kjui / rjui）の変更は bed に入らない。**

実例: 「失敗した段を最後で名乗る」を bed で撃ったが**発火しなかった**。Python 側は worktree の
コードだが、**行を書くのはツール側**で、そのツールは前のリリース版だった。⇒ **Python 側の
変更だけが効いている、という中途半端な条件で測っていた。**

```
bed でツール側の変更を測る前に:
  <worktree>/jui_tools/bin/jui sync_tool --from <worktree>
確認:  Source: <worktree>  (X.Y.Z, --from)      ← 出所と理由を名乗るので証拠になる
       grep -rl "<新しい識別子>" <bed>/<face>/<tool>_tools/   ← 実際に入ったか
```

📌 **`jui` のランチャが自分の置き場所から解決する**（別項）のと**同じ族**で、⇒ **層が 2 つある**:
**どの Python が走るか**と**どのツールが走るか**は別に決まる。**版名はどちらも区別しない。**

## 窓を聞くとき、基準値の版も同じ 1 通で聞く

⚠️ **「基準値は動きません」は起点を言わないと意味を持たない。** 実例: 1.8.12 の配布で列車は
**1.8.11 → 1.8.12 の差**を根拠に「動きません」と 7 面へ配った。⚠️ **2 面は基準値が 1.8.10** で、
**1.8.11 の変更（ブロックの 2 行分割）を今回はじめて見た。** ⇒ **2 面が独立に「分子が消えた」と
誤報し、1 面は起票した。**

⇒ **窓の質問に 1 行足す**: **「あなたの基準値はどの版ですか」**。同じ 1 通で聞ける。

## 一致が独立になるのは、構成が違うときだけ

⚠️ **同じ CLAUDE.md・同じゲート構成・同じ読み方の癖を共有する面どうしの一致は、
構造的に独立にならない。** 実例: 上の誤報は 2 面から**別々に**届いたが、**両方とも 1 行目だけを
読み、両方とも基準値が 1.8.10** だった。⇒ **同じ計器・同じ習慣を持つ 2 人の一致は、
独立な確認ではない。**

⇒ **系列を共有する面は 1 面ぶんとして数える。** 独立が要るときは**別系列の面に聞く**。

📌 その誤報の原因は読み方だった —— `grep -E 'generation manifest|Build completed'` は
**続き行（`  this run: …`）にマッチしないので出力に現れない**。⚠️ **落とした行が、同じ面が
別途報告していた欠陥の直接証拠**でもあった（`recorded/updated 215` が、分母の差から遠回りに
割り出した 215 と同じ数）。⇒ **grep で読んだログは「無い」と「マッチしない」を区別しない。**

## 刈る前に理由を残す —— ただし「欠陥の副作用」として説明すると、刈った時点で消える

**列車は「なぜ片方の test ツリーが記録に入り、もう片方は入らないのか」を、刈る前の条件に
した。** 理由: **説明されないまま両方を刈ると、刈った理由が後から再構成できない。**

⚠️ **より重要な形が測定で出た** —— **問いは 2 つに分かれており、独立だった**:

```
問 A  なぜ mocks が入らないか   → パスが platform 配下でないから（構造・一貫している）
問 B  なぜ unit の 14 件が偽か  → generatedBy: "jui build" が偽（別ツールの産物）
```
⇒ **unit が入っているのは A の規則どおりで、例外ではない。偽なのは B の主張だけ。**
⇒ **刈るのは B の修正で、A の説明は刈った後も残る。**

📌 **逆に、A を「B の副作用」として説明していたら、刈った時点で説明が消えていた。**
⚠️ 実際にその形の推論が出ていた（「`jui build` が書かない生成物は入らない」）。
**それだと unit が説明できず、「例外」と呼んで済ませることになる。**

⇒ **安定した振る舞いを、欠陥の副作用として説明しない。** 欠陥を直すと説明も消えるので、
**次の読み手はその振る舞いを再発見しなければならない。**

⚠️ **列車の側の同型**: 「`jui build` が書かないのに自分が書いたと記録していた」を 5 面へ配った。
**主張が偽なのは正しい。** ⚠️ **しかし「入っていた理由」を存在しない規則で説明していた** ——
**入っていたのは到達可能性と拡張子で、「jui build が書くか」は一度も判定に使われていない。**
⇒ **「主張が偽である」と「なぜそう主張したか」は別の命題。**

## ⚠️ 道具の壊れ方には、欠落と並べ替えの 2 種類がある

```
deploy.sh のパイプ終端が exit code を洗う     → 欠落
gate_baseline の sed -n '1,40p' が本文を洗う   → 欠落
grep が続き行を落とす                          → 欠落
> log 2>&1 が行順を洗う                        → ⚠️ 並べ替え
```
⇒ **欠落は「足りない」ので探しに行ける。並べ替えは出力が完全なので、正しく見える。**
⚠️ **探す動機が出ないぶん、並べ替えのほうが長く生き残る。**

**実測**: `> log 2>&1` では **stdout はファイル向けにブロックバッファされ、stderr は素通し**。
```python
print("stdout 1"); print("stdout 2")
print("ERROR: 最後に emit", file=sys.stderr)     # ソース上は 3 番目
for i in range(3, 8): print(f"stdout {i}")
```
```
1  ERROR: 最後に emit        ← 最後に emit したものが 1 行目
2  stdout 1
```
⇒ **ログの行順から実行順を読まない。** 実例: 2 レーンが同じログから同じ誤った機序
（「ERROR が先頭に在るのに build は先へ進んだ ⇒ 遅延 halt」）に着き、列車がそれを
「手掛かり」として実装レーンへ転送した。⚠️ **2 面の一致は、同じログを同じ道具で読んだ一致。**

## 「撃った」は「効いた」ではない —— 効果を別の観測で確かめる

**終了コードが「やった」と「やることが無かった」の両方から予測される操作**が多い。

```
simctl uninstall <存在しない id>   EXIT=0（実測）  ⇒ 「消した」と「対象が無かった」が同じ
ps | grep 'jui$'  が 0 件          ⇒ 「走っていない」と「その名前では映らない」が同じ
                                     （実例: mock server は走っていたが comm が python3 系で映らない）
sync_tool EXIT=0                   ⇒ 「配った」と「配る先が無かった」が同じ
```
⇒ **操作の成功ではなく、効果を別の観測で確かめる。**
```
uninstall  → listapps の前後
配布       → 配布の前後で消費側の版を読む（receipts / sync-meta.json）
プロセス   → 名前ではなく構造で答える（「配布が壊すのは新規の起動だけ」）
```

⚠️ **実例**: 列車は 1.8.9 の配布が無害だったことを `ps` の 0 件で示した。⇒ **弱い計器**で、
**しかも配布の 6 分後に撃っている**（「今」しか答えない道具を、過去について使った）。
別の面は「決定論的初回状態のため uninstall」を撃ったが **bundle id の綴りが違い**、
**EXIT=0 で黙って no-op** —— **気づいたのはログで id を読んだからで、終了コードからは永久に
分からない。**

📌 **今日の道具の分類に 3 つ目が付く**:
```
欠落      足りないので探しに行ける
並べ替え  出力が完全なので正しく見える（> log 2>&1）
no-op     ⚠️ 成功したように見える。成功と「対象が無い」を終了コードが区別しない
```

## 通知は「増えたもの」ではなく「変わったもの」を数える

⚠️ **1.8.13 の通知は「2 行増える」と書いた。実際に消費側の装置を壊したのは、増えた行ではなく
既存の行の綴り**:
```
1.8.12   this run: recorded/updated 0                 ← 消費側の規則 s|^\( *this run: \).*| に当たる
1.8.13   this run (jui 1.8.13): recorded/updated 0    ← 当たらない
⇒ そのまま --update すると生の数が焼かれ、fresh clone で初めて鳴る
```
📌 **予告の項目数と、受け手の装置に当たる項目数は別**（消費側の整理）。⇒ **「新しく増えた行」を
数えると、既存の行の変更が落ちる。**

⚠️ **列車は新しい出力を目の前に持ち、消費側の規則も知っていて、それでも「1 行足すだけ」と
書いた。** ⇒ **突き合わせれば機械的に分かることを、突き合わせずに助言した。**
⇒ **通知を書く前に、消費側の正規表現に実出力を通す。**

📌 **実装側の同型**: 「1 行 1 主語にする」という**設計の説明は、変更点の一覧ではない。**
⇒ **「消費側の文字列一致が壊れる箇所」を別の欄で数える。**

## 「完了」と「成功」を混同しない —— 結論の語を読む

⚠️ **CI ウォッチャーの break 条件が「全 run が completed」で、success を要求していなかった。**
```

⇒ 「FINAL」だけを見ると緑と区別が付かない
```
**今回は tip の CI を別に確認していたので実害は無かったが、`FINAL` を見て打っていたら
cancelled にタグを打っていた。** ⇒ **結論の語（success / cancelled / failure）を必ず読む。**

⚠️ **消費側から 1 段の追加**: **その語は実行形式で変わり得る**
（`xcodebuild test` は `** TEST SUCCEEDED **`、`test-without-building` は
`** TEST EXECUTE SUCCEEDED **`。同じ grep で片方が読めない）。
⇒ **語を固定で探すなら、その語がその実行形式のものであることも確かめる。**

## 強制ゲートは、呼び先の終了コードだけに依存しない

**「必須と定めた手順が構造的に空だったのに、債務が 0」**が 2 例あり、**理由が違った**:
